# A compiler on Windows

On Windows a PC build needs a C++ compiler that the tool can reach without a terminal set up for it. Visual Studio is found through `vswhere`, which its installer always places in the same folder, by FriedCore's `visualStudioCmake`, since Fried Editor needs the same answer to build its player, and drives itself once CMake picks its generator, so a CMake is all the build needs from it: the one on the `PATH`, or the one the C++ workload installs inside Visual Studio. Without Visual Studio, the tool keeps a w64devkit of its own in its local data folder rather than asking for one on the `PATH`, since w64devkit is made to be used from the terminal it opens and nothing else sees it. Its version and SHA-256 are fixed in the tool, so every machine builds with the same GCC.

A web build with no Emscripten SDK offers to download one, the way a PC build on Windows offers w64devkit. `emscripten_sdk.cpp` clones emsdk into the tool's data folder and installs and activates the one Emscripten release the engine was tested with, as three commands in the same dialog. Unlike w64devkit it cannot be unpacked elsewhere and moved, since activating writes absolute paths, so it is installed in place and `finishInstall()` deletes what a failed install left. An SDK is looked for in `EMSDK`, then that copy, then `~/emsdk`, and counts only if it holds the toolchain file.

The download runs in the command window like any build, as three commands: `curl.exe` and PowerShell's `Get-FileHash`, both part of Windows 10 and later, and the archive itself, a 7-Zip self-extractor that unpacks without asking when given `-y`. It unpacks into a folder of its own and is moved into place only once it is complete, so a download that was stopped never looks installed. Its tools are named by absolute path, and its `bin/` is put first on the `PATH` of the processes the build starts, for whatever CMake and GCC look up there.
