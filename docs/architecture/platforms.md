# Platforms

What the build bar lists is a `BuildTarget`, a build directory, a toolchain file and nothing else. Targets and platforms are separate because Windows from Linux is one more thing to build but not one more platform: its game is the PC one, with the PC's display and icon, so `platformOf()` maps it to `Platform::Pc` and the project pages never see it. It is listed only off Windows, where building for Windows is what `PC` already does. The web is a platform to the engine, with a section of its own in `project.fried`, but the tool has no page for it: `pageOf()` puts its target on the PC's page, beside Windows. The tool never tells the engine's CMake which platform it is building for: the toolchain file does that by setting `VITA`, `NINTENDO_SWITCH`, `NINTENDO_3DS` or `NINTENDO_DS`, by naming its platform in `FXSDK_PLATFORM_LONG` for the fx-CG50, or, for Windows, by setting `CMAKE_SYSTEM_NAME`, so the pipeline is the same three commands everywhere and adding a target here is a case in two functions rather than a new code path.

The commands a target runs, and the lookup of the SDKs below, are FriedCore's `Build::steps` and `detectToolchains`: `build.cpp` only hands them the folders the tool downloads into and, on Windows, the Visual Studio that `vswhere` finds, which is the one thing FriedCore cannot ask for. The command window keeps `QProcess`, which is proven on Windows, and takes what kind of line each is from FriedCore's `kindOf`.

Each SDK is found through its own environment variable (`VITASDK`, `DEVKITPRO`, and `EMSDK` for the web, with `~/emsdk` and then the tool's own copy as fallbacks, whose toolchain file is under `upstream/emscripten/` there) and checked for the toolchain file before anything runs, so a missing SDK is one dialog rather than a build that dies halfway. Both variables are normally exported from a shell profile, which a tool launched from a desktop menu may never have inherited. The fxSDK exports no variable, so its toolchain is found from the `fxsdk` command on the `PATH`, which it installs in the `bin/` beside the `lib/cmake/fxsdk/` holding the toolchain file. The MinGW-w64 toolchain file belongs to the engine rather than to an SDK, so it is taken from the project's `engine/` submodule, or from the directory above for the engine's own sandbox, which sits inside the engine, and the cross compiler it names is checked on the `PATH` first.

The build directory and build type are remembered per project and per target, so a project can keep symbols on PC while its console build is optimized. Only the CMake build tree moves with that field: `build.hxml` writes the generated C++ to `build/cpp` and `fried_add_game()` reads it from there, so where that lands is the engine's to decide and not the tool's. The build type reaches CMake twice, as `-DCMAKE_BUILD_TYPE` when configuring and as `--config` when building, because a generator that holds every configuration at once ignores the first and reads the second. The type reaches Haxe too, through the same command on every target: Debug adds `-debug`, which is the define the engine's `Log` checks to print the call site under each message, and the build bar's **Log to file** checkbox adds `-D fried_log_file`, which compiles the engine's log file in. Neither is a CMake setting, because both are decided when the Haxe compiler runs, before CMake is configured.

A platform's page shows its toolchain through `ToolchainPanel`, which asks `Build::commands()`, `needsCompilerDownload()` and `needsEmscriptenDownload()` rather than checking for tools itself, so what a page says can never disagree with what a build does. It lists the commands for the build bar's own settings, and the bar's `changed()` signal refreshes it.

VitaSDK's packaging step does not quote the paths it is handed, so a space anywhere in a Vita project's path lets it compile but not be packaged. New Project avoids it by putting `My Demo Game` in `My-Demo-Game` while the project keeps the name as typed, and the build form warns when a path it cannot rename has one. `elf2nro` quotes its arguments, so the Switch needs none of this.
